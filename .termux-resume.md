## ABERTO: app travado no splash (começou depois da 5.9.2) — investigar primeiro
**Sintoma**: abrir o Pulsa deixa na tela da imagem da Virgin (só a imagem, sem botão) e não
passa para a tela principal. Não é crash: `showCrashFallback` (`MainActivity:190`) dumpa o
stack trace na tela quando `createMain` lance exceção, e nada aparece. Então é **main thread
bloqueada ou loop de morte do processo**.

O que JÁ foi descartado por leitura de código (não repetir isso):
- `OrbitRingsView`: o diff da T0.2 nele é 100% cosmético (só `0x88B6FF2E` → `R.color.*`),
  zero mudança de loop. Descartado.
- `TamiRadio.speakClock()` (código novo do 5.9.2): só roda 30s após o launch e só na virada
  de hora (`handler.postDelayed(tick, POLL_MS)`, com guarda `MINUTE == 0`). Não trava o splash.
- Não há SplashScreen API (`installSplashScreen`/`setKeepOnScreenCondition` não existem no
  projeto): o "splash" é só o `windowBackground` do tema.
- `Migrations.run()`: lista finita, tudo em try/catch. `RemoteSync.start()`/`MirrorSync.start()`
  só postam em handler, não fazem rede na main thread.
- O caminho de boot inteiro foi lido: `PulsaApp.onCreate` → `Migrations` → `RemoteSync` →
  `MainActivity.onCreate` → `createMain`. **Nada que eu tenha escrito bloqueia a main thread.**

**Hipótese mais forte agora**: o Android está matando o app por falta de memória. Esse aparelho
sobreviveu a builds de 12min de Gradle; com os daemons segurando RAM, o app abre, pede memória e
morre no splash antes de rodar qualquer código. → **TESTE FEITO PELO USUÁRIO: fechar o Termux
inteiro, esperar ~10s, abrir o Pulsa.** Se entrar, era isso.

Se NÃO entrar, o próximo passo é pedir **versão do Android + RAM total** e fazer build de
diagnóstico. Atenção: se o app não abre, o UpdateChecker é inalcançável — a instalação tem de
ser pelo navegador, em `https://cleberleonheart-maker.github.io/pulsaweb/Pulsa.apk`.

## Bugs achados na leitura de 25/09 — AINDA NAO CORRIGIDOS, nenhum build feito
1. **`HotwordService.onCreate` retorna sem `startForeground`** (`dj/HotwordService.kt:34-38`):
   ```
   if (!staying()) { stopSelf(); return }   // sem startForeground
   ...
   startForeground(NOTIF_ID, notification())
   ```
   Mas o serviço é iniciado com `ContextCompat.startForegroundService` (`dj/Hotword.kt:33`).
   No Android 12+ isso estoura `ForegroundServiceDidNotStartInTimeException` e **mata o
   processo** → splash → reinicia → splash. Loop. `staying()` = `Settings.hotword &&
   Playback.isPlaying && micGranted()`; `startIfNeeded` checa as mesmas 3 condições antes, então
   a janela é estreita, mas `onStartCommand` é `START_STICKY`: após morte do processo, o
   reinício entra com `Playback.isPlaying == false` → `staying()` falso → `stopSelf()` sem
   `startForeground`. **Correção**: chamar `startForeground` incondicionalmente no topo do
   `onCreate` e decidir o `stopSelf()` depois.
2. **UpdateChecker trava o update para sempre** (`util/UpdateChecker.kt:136` e `handle()`):
   `markAttempted` grava `attempted_name` logo **depois do download, antes de confirmar a
   instalação**; e `handle()` faz `if (attempted_name == latestName) return`. Se o download
   completa mas a instalação falha ou o usuário cancela, o app **nunca mais oferece aquela
   versão**. `clearAttempted()` só é chamado quando o *download* falha, nunca quando a
   *instalação* falha. **Correção**: marcar só após instalar com sucesso, ou janela curta de
   cooldown + limpar no start quando `BuildConfig.VERSION_CODE` ainda é menor que o tentado.
3. **Microfone ainda reinicia sem backoff**: em `DjCommandListener.onResults`, texto vazio dá
   `emptyCount++` e chama `restart()` na hora — o backoff exponencial só cobre `onError`, e
   `emptyCount` não influencia nada. O usuário **repitiu** que o microfone continua abrindo
   depois da 5.9.1. **Correção**: texto vazio também tem que passar pelo atraso.

- O código está em `/root/pulsa` e **sobrevive**: reabrir o Termux e `cd /root/pulsa`.
- Só o que está em `/tmp/opencode/` se perde (é tmpfs, limpa no reboot): logs, APKs de backup e
  snapshots do `res/`. A baseline do gate foi por isso movida para dentro do repo, em
  `scripts/baseline/`. Não dependa de `/tmp` para nada que precise durar.
- Build/teste em andamento morre junto com o app — só retomar rodando de novo.
- Antes de qualquer coisa em XML: rodar o gate, porque ids de recurso mudam a cada token novo.

2. **Microfone abrindo sem par** (mãos-livres)
   - O laço era `onResults -> restart()` com `minGapMs = 3000`, ou seja, o mic ligava e
     desligava a cada ~3s para sempre enquanto a música tocava.
   - Nao há mic duplicado: `Playback.setMicListening` é flag única e o `HotwordService` e a
     Virgin da tela dividem o mesmo caminho. Não mexer nisso ao "consertar".

## Regra do aparelho (importante)
- **Aparelho do usuário: Redmi 14C** (entrada, SoC fraco, 3-4 GB de RAM, HyperOS). Android
  13/14 => a regra de foreground service do Android 12+ **se aplica nele**.
  Build pesado neste aparelho é particamente perigoso para o app, não só lento.
- Este celular é a máquina de build **e** o aparelho de uso. Build pesado (Gradle + kotlinc +
  aapt2 em qemu, 2 CPUs) **congela o Pulsa na mão do usuário**: aconteceu em 25/09, o app ficou
  "não está respondendo" até o build ser morto (load 2 -> 0.12).
- **Consequência provável do splash travado**: RAM esgotada pelos daemons do Gradle + o
  killer do HyperOS, o app morre antes de desenhar. Foi por isso que o primeiro teste é
  fechar o Termux inteiro. Build/teste com o HyperOS reclamando de "autostart" também conta
  como "o sistema mata o app sozinho".
- Antes de rodar build/teste, **avisar** e só rodar com o usuário dizendo que não está usando o
  app. Alternativas: `--max-workers=1`, `nice -n 19`, e builds só em janela ociosa.
- Nada disso chegou ao servidor: o APK publicado (`123|5.9.2`) tem 5.9.0+5.9.1+5.9.2.
