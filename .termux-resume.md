## Build local: usar o CI + o script (MEDIDO 27/09)
O Gradle local **não termina** neste aparelho, e não é impressão:
- `./gradlew :app:testDebugUnitTest` → 40min, sem saída, sem artefato novo;
- `./gradlew -q projects --no-daemon` → **4min40 de relógio, 7s de CPU no cliente**;
- Gradle Daemon morrendo como `STOPPED (by user or operating system)`.
O CI faz testes + `assembleRelease` em **3–4min** (o aparelho dele é que é rápido).
Então: **1 commit = 1 CI**, e o parecer final de cada passo da F1 é CI + checklist manual.

Para não esperar o CI a cada linha digitada, existe
**`scripts/verificar-rapido.sh`** (type-check + JUnit sem Gradle, com o
`kotlin-compiler-embeddable` do cache):
```bash
scripts/verificar-rapido.sh            # compila o que o branch mexeu (~1min)
scripts/verificar-rapido.sh --testes   # + roda as 6 suites (68 testes) (~4min, 1ª vez monta o classpath)
scripts/verificar-rapido.sh --tudo     # app inteiro (~10min)
```
Ele **não** cobre XML, manifest, dex, assinatura nem dependência que ainda não baixou — o
CI segue sendo o juiz. Duas armadilhas já documentadas no script: no classpath entra só a
stdlib 1.9.24 (senão `buildList` dá "unresolved") e só a versão mais alta de cada módulo;
e compilar um arquivo sozinho pega o `.class` velho dos outros.


## Splash travado: causa candidata forte, CORRIGIDA na 5.9.3 — falta o usuário confirmar
**Sintoma (25/09)**: abrir o Pulsa deixa na tela da imagem da Virgin (só a imagem, sem botão) e
não passa para a tela principal. Não é crash: `showCrashFallback` (`MainActivity:190`) dumpa o
stack trace na tela quando `createMain` lance exceção, e nada aparece. Então é **main thread
bloqueada ou loop de morte do processo**.


O que JÁ foi descartado por leitura de código (não repetir isso):
- `OrbitRingsView`: o diff da T0.2 nele é 100% cosmético (só `0x88B6FF2E` → `R.color.*`),
  zero mudança de loop. Descartado.
- `TamiRadio.speakClock()` (código novo do 5.9.2): só roda 30s após o launch e só na virada
  de hora (`handler.postDelayed(tick, POLL_MS)`, com guarda `MINUTE == 0`). Não trava o splash.
- Não há SplashScreen API (`installSplashScreen`/`setKeepOnScreenCondition` não existem no
  projeto): o "splash" é só o `windowBackground` do tema.
- `Migrations.run()`: lista finita, tudo em try/catch. `RemoteSync.start()`/`MirrorSync.start()`
  só postam em handler, não fazem rede na main thread.
- O caminho de boot inteiro foi lido: `PulsaApp.onCreate` → `Migrations` → `RemoteSync` →
  `MainActivity.onCreate` → `createMain`. **Nada que eu tenha escrito bloqueia a main thread.**

**Hipótese mais forte agora**: o Android está matando o app por falta de memória. Esse aparelho
sobreviveu a builds de 12min de Gradle; com os daemons segurando RAM, o app abre, pede memória e
morre no splash antes de rodar qualquer código. → **TESTE FEITO PELO USUÁRIO: fechar o Termux
inteiro, esperar ~10s, abrir o Pulsa.** Se entrar, era isso.

**O que a 5.9.3 resolveu (bug 1 da lista de baixo)**: o `HotwordService` era iniciado com
`startForegroundService` e podia voltar do `onCreate` sem `startForeground()` (e com
`onStartCommand` = `START_STICKY`, o reinício do processo caía sempre no caminho do `stopSelf()`).
No Android 12+ isso é `ForegroundServiceDidNotStartInTime` → **o sistema mata o processo** →
splash → reinicia → splash. É exatamente o sintoma descrito. Agora o `startForeground()` é
chamado no topo do `onCreate` e a decisão de `stopSelf()` vem depois.
**Se a 5.9.3 ainda não abrir: pedir a versão do Android + RAM total e fazer build de diagnóstico.**
Atenção: se o app não abre, o UpdateChecker é inalcançável — a instalação tem de ser pelo
navegador, em `https://cleberleonheart-maker.github.io/pulsaweb/Pulsa.apk` (é o `124|5.9.3`).

## Bugs achados na leitura de 25/09 — os 3 CORRIGIDOS e publicados na 5.9.3 (124)

1. **FEITO na 5.9.3** — `HotwordService.onCreate` retornava sem `startForeground`
   (`dj/HotwordService.kt:34-38`):
   ```
   if (!staying()) { stopSelf(); return }   // sem startForeground
   ...
   startForeground(NOTIF_ID, notification())
   ```
   Mas o serviço é iniciado com `ContextCompat.startForegroundService` (`dj/Hotword.kt:33`).
   No Android 12+ isso estoura `ForegroundServiceDidNotStartInTimeException` e **mata o
   processo** → splash → reinicia → splash. Loop. `staying()` = `Settings.hotword &&
   Playback.isPlaying && micGranted()`; `startIfNeeded` checa as mesmas 3 condições antes, então
   a janela é estreita, mas `onStartCommand` é `START_STICKY`: após morte do processo, o
   reinício entra com `Playback.isPlaying == false` → `staying()` falso → `stopSelf()` sem
   `startForeground`. **Correção**: chamar `startForeground` incondicionalmente no topo do
   `onCreate` e decidir o `stopSelf()` depois.
2. **FEITO na 5.9.3** — `UpdateChecker` travava o update para sempre
   (`util/UpdateChecker.kt:136` e `handle()`):
   `markAttempted` grava `attempted_name` logo **depois do download, antes de confirmar a
   instalação**; e `handle()` faz `if (attempted_name == latestName) return`. Se o download
   completa mas a instalação falha ou o usuário cancela, o app **nunca mais oferece aquela
   versão**. `clearAttempted()` só é chamado quando o *download* falha, nunca quando a
   *instalação* falha. **Correção**: marcar só após instalar com sucesso, ou janela curta de
   cooldown + limpar no start quando `BuildConfig.VERSION_CODE` ainda é menor que o tentado.
3. **FEITO na 5.9.3** — microfone reiniciava sem backoff: em `DjCommandListener.onResults`,
   texto vazio dava `emptyCount++` e chamava `restart()` na hora.

  sobe/desce foreground via provider de notificação). Metadata vem dos `MediaItem` (embutida no
  `prepareCurrent`; `publishMetadata` vira `replaceMediaItem`). Comandos externos: play/pause/seek
  tocam o player pelo default do Media3 (`COMMAND_PLAY_PAUSE`, idempotente) e o bookkeeping vem de
  `onIsPlayingChanged` → `syncExternalPlaybackState`; next/prev/stop **bloqueados** no
  `onPlayerCommandRequest` (evita segundo pulo na fila recriada e mantém o stop como no-op).
- **Não mexer nisso sem ler:** o `PlaybackService` se anuncia na fachada **no `onCreate`**, e não
  no `bindService` — é o que deixa o widget (que não conecta nada, é um receiver) desenhando a
  faixa tocando, e o motor continuar valendo depois do `unbind` também é proposital.
- **Verdades da API do media3 1.3.1 confirmadas no jar** (não confiar em chute): `ExoPlayer.Builder`
  NÃO tem `setAudioSessionId` (só `ExoPlayer.setAudioSessionId` pós-build) e `Player` NÃO tem
  `setVolume(float,float)` — por isso o pan estéreo do 8D não se reproduz 1:1; `Player.Listener`
  tem `onAudioSessionIdChanged(int)`; `setMediaItems(List, int, long)` existe. `@OptIn(UnstableApi::class)`
  na classe resolve o compilador Kotlin.
- Regra: a F1 vive em `feature/media3`. A `main` continua sendo o app que o povo recebe.

- Para publicar uma Mudança do usuário na `main` enquanto a F1 corre: bump de `versionCode`

  "Invalid unicode escape sequence in string".- `aapt2 dump xmltree` aceita VÁRIOS `--file` numa só invocação: 146 recursos em 9s, contra
  ~8min chamando um por vez. O `--values` do aapt2 do SDK não resolve referência de recurso

  garante que o "final" voltou igual ao que estava verificado.

  `REMOTE_CODE >= CODE`; por isso commit sem bump de `versionCode` é publicação inócua, e é assim
  que se manda trabalho não-released sem Arriscar o APK em produção.

  `@drawable/ic_splash` (a Virgin). "Travou no splash" e "caiu no login" podem ser a mesma
  imagem na tela. Mas `MainActivity:153` só vai pro login se `Account.loggedIn()` for falso, e
  nesse caso apareceriam os botões — se a tela é **só a imagem**, não é o login.
- **Antes de culpar uma mudança minha por um bug novo, ler o caminho de boot inteiro** e
  descartar por leitura: `PulsaApp.onCreate` → `Migrations.run` → `RemoteSync/MirrorSync.start`
  → `MainActivity.onCreate` → `createMain`. E lembrar que **exceção ≠ travamento**: existe
  `showCrashFallback` que mostra o stack trace na tela, então tela em branco/presa sem texto

  splash que não tem nada a ver com o código que a pessoa acha que quebrou.
